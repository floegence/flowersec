<p align="center"><strong>Создавайте безопасные соединения между приложениями, не управляя транспортами.</strong></p>
<p align="center">Flowersec предоставляет Go, TypeScript, Swift и Rust единую модель сеансов со сквозным шифрованием, встроенными RPC, уведомлениями и байтовыми потоками.</p>

<a id="why-flowersec"></a>

## Зачем нужен Flowersec

- Все четыре SDK используют одну безопасную модель сеансов, поэтому приложения могут повторно использовать сценарии RPC и потоковой передачи данных.
- Используйте поддерживаемые сетевые соединения без переписывания кода приложения для каждого варианта.
- RPC, уведомления и байтовые потоки работают в одном аутентифицированном соединении со сквозным шифрованием.
- Даже через ретранслятор данные приложения остаются зашифрованными; ретранслятор только пересылает шифротекст.

<a id="how-it-works"></a>

## Как это работает

| Маршрут | Схема соединения | Транспорт потоков |
| --- | --- | --- |
| Direct | Клиент подключается к конечной точке через совместимый вариант транспорта | WebSocket использует Yamux в пределах одного перехода; транспорты семейства QUIC используют нативные двунаправленные потоки |
| Tunnel | Клиентское и серверное плечи соединяются через независимо выбранные совместимые транспорты | Туннель сопоставляет зашифрованные потоки между плечами, не назначая основной транспорт |

Raw QUIC и WebTransport сохраняют нативное поведение FIN, RESET_STREAM, STOP_SENDING, управления потоком и миграции. Flowersec отключает 0-RTT приложения. Надёжные потоки никогда не используют QUIC DATAGRAM; среды с согласованной нативной поддержкой DATAGRAM предоставляют её только через независимые от транспорта ненадёжные сообщения.

## Локальный запуск

Запустите стандартный набор приёмочных тестов:

```bash
make test
```

После исправления сбоя используйте `make test-resume`, чтобы продолжить с первого незавершённого теста до следующего сбоя или результата `ALL GREEN`. Завершённые ID остаются действительными при изменении исходного коммита.

Команда `make coverage-race` запускает четыре языковых набора покрытия и эксклюзивный Go race. `make browser-smoke` проверяет три локальные топологии Chromium, а `make browser-compat` явно проверяет возможности Firefox/WebKit. Для привилегированной диагностики слабой сети и ядра используйте `make diagnostic`; для тестов ёмкости и soak — `make performance`.

## SDK и практические примеры

| Язык | Пакет | Публичная точка входа |
| --- | --- | --- |
| Go | `github.com/floegence/flowersec/flowersec-go/v2` | `flowersec.ParseArtifact`, `flowersec.Connect`, `flowersec.NewConnectionController`, `flowersec.NewAcceptor` |
| TypeScript | `@floegence/flowersec-core` | непрозрачные точки входа v2 в корне пакета, `/browser`, `/node` и `/proxy` |
| Swift | Продукт SwiftPM `Flowersec` | `Artifact`, `connect`, `Session` |
| Rust | crate `flowersec` | `Artifact`, `connect`, `Session` |

Сервисные control plane на Go используют отдельный пакет `github.com/floegence/flowersec/flowersec-go/v2/controlplane` для выпуска непрозрачных artifacts и обработки authorization callback от `flowersec-runtime`.

[Указатель практических примеров](examples/README.md) содержит только примеры v2 и команды проверки.

## Возможности SDK

Ниже возможности сгруппированы по сценариям, которые разработчики приложений используют напрямую, а не по внутренним объектам протокола. Каждый профиль SDK объявляет собственную границу среды выполнения и платформы. Ограничение платформы можно отметить как неподдерживаемое только при наличии в `stability/language_capabilities.json` явной причины, альтернативной публичной границы и исполняемого ID теста. Постоянное хранилище control plane является границей сервиса: клиенты вызывают аутентифицированный сервис, использующий `flowersec-go/v2/controlplane`, и не встраивают второй issuer или datastore. Удобство конкретного языка адаптирует синтаксис или оркестрацию к экосистеме, не меняя общие сценарии. Поведение восстановления соединения описывается структурированной disposition контроллера.

| Возможность | Go | TypeScript | Swift | Rust |
| --- | :---: | :---: | :---: | :---: |
| Сквозные зашифрованные сеансы, RPC и байтовые потоки | Да | Да | Да | Да |
| Автоматическое восстановление длительных соединений | Да | Да | Да | Да |
| Ненадёжные сообщения | Да | Да | Нет | Да |
| Получение уведомлений RPC | Нет | Да | Нет | Нет |
| Обработка входящих запросов RPC | Да | Нет | Нет | Нет |
| Клиентские соединения WebSocket | Да | Browser и Node.js | macOS и iOS | Нет |
| Клиентские соединения raw QUIC | Да | Нет | Нет | Да |
| Клиентские соединения WebTransport | Да | Browser и Node.js | Нет | Нет |
| Приём сеансов на сервере | `NewAcceptor` | `createAcceptor` / `AcceptedSession` | Не поддерживается профилем listener Apple | `Acceptor::bind` / `accept_with_handlers` |
| Выпуск артефактов и авторизация через control plane | `flowersec-go/v2/controlplane` | Не поддерживается; граница сервиса приложения | Не поддерживается; граница сервиса приложения | Не поддерживается; граница сервиса приложения |

Принимаются только объявленные комбинации транспортов; неподдерживаемые комбинации завершаются безопасным отказом. Каждая строка подтверждена промышленным кодом коннектора и явным ID теста в `stability/language_capabilities.json`. Для неподдерживаемых возможностей указаны причина и альтернативная граница. Данные о возможностях и выбор транспорта остаются внутренними деталями.

## Безопасность

- Артефакты являются непрозрачными дескрипторами ограниченного размера и однократного использования. Расходование фиксируется в постоянном хранилище до отправки первого байта учётных данных.
- Транспорты семейства QUIC требуют TLS 1.3, точного совпадения ALPN, явно заданных корней доверия и отключенной ранней передачи данных.
- Публичные ошибки не содержат чувствительных данных и ограничены по размеру; сведения о кандидатах, сетевом формате, ключах и журнале состояния остаются внутренними.
- Структурированные disposition контроллера разрешают только новую попытку со свежим артефактом; они не переиспользуют учётные данные и не повторяют работу из завершённого сеанса.
- Отмена сеанса, сроки выполнения, FIN, сброс, проверка активности, смена ключей и очистка имеют чёткие временные и ресурсные границы.

См. [архитектуру Transport v2](docs/TRANSPORT_V2_ARCHITECTURE.md) и [модель угроз](docs/THREAT_MODEL.md).

## Развёртывание и разработка

Среда выполнения Flowersec предоставляет готовые к промышленной эксплуатации реализации входящих соединений WebSocket, raw QUIC и WebTransport. SDK приложений получают только непрозрачные артефакты и сеансы; CLI среды выполнения компонуют те же реализации connector и acceptor.

Установите хуки репозитория и запустите основную проверку перед интеграцией:

```bash
make install-hooks
make precommit
```

`scripts/push-main.sh` запускает ограниченный локальный набор приёмочных тестов перед отправкой точного SHA ветки main. Полная инженерная проверка и явные workflows nightly, diagnostic и performance охватывают совместимость, привилегированную диагностику и нагрузочные тесты; сам выпуск тесты не запускает.

Flowersec распространяется по [лицензии MIT](LICENSE). Артефакты релизов публикуются через [GitHub Releases](https://github.com/floegence/flowersec/releases).
